## Assignment
Build Obico Failure Detection Service — backend integration for AI-powered print failure detection using external ML API.

## Deliverables

### Code
- `IObicoFailureDetectionService` — Interface for failure detection service
- `ObicoFailureDetectionService` — HTTP client for Obico ML API; queries printer status, analyzes images, broadcasts failures via SignalR
- `PrintFailureMonitorService` — Background worker; runs scan cycles every 30s (configurable 10-300s)
- `FailureDetectionController` — REST API with 3 endpoints:
  - `GET /api/failure-detection/status` — Returns service health
  - `POST /api/failure-detection/analyze` — Manual failure analysis
  - `GET /api/failure-detection/history` — Event history (stubbed)
- `ObicoSettings` — Configuration entity with validation (disabled by default, confidence threshold 0.7)
- `FailureDetectionDto` — Response DTO for detected failures

### Architecture Decisions
1. **No Database Persistence** — Events are transient, broadcast via SignalR
2. **Uses Printer Status Cache** — Queries `IPrinterStatusCacheReader` to avoid repeated EF queries
3. **Auto-Pause Stubbed** — Setting exists but actual pause requires backend client integration (future)
4. **Configurable via ObicoSettings** — Opt-in feature with adjustable thresholds
5. **Named HttpClient** — "ObicoML" with 15s timeout for image analysis

### Issues & Fixes
**DI Scoping Bug (Critical):** Background service `PrintFailureMonitorService` (singleton) tried to resolve `IObicoFailureDetectionService` (scoped) directly, causing InvalidOperationException. 
- **Fix:** Injected `IServiceScopeFactory`, created scope per scan cycle, resolved service from scope.

**JSON DTO Warnings:** All cost DTO properties had `{ get; set; }`, causing ESLint warnings.
- **Fix:** Changed to `{ get; init; }` for immutability.
