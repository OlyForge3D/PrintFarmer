## Refined Goal

Make the existing PrintFarmer queue the single durable, authorized execution
path for generated filament-calibration G-code. Queue creation must be
canonically idempotent and transactionally produce durable work; every
manual, scored, batch, automatic, Desktop-facing, generic-status,
rerun/requeue, and scheduler start path must acquire the same database-backed
printer/job claim before network I/O. Calibration starts must remain safe
under concurrency, process crashes, stale state, uncertain backend outcomes,
and exact-job bed-clear changes while existing standard queue clients remain
compatible.

The implementation must use the prerequisite calibration records and
promoted immutable `GcodeFile` generated by the merged dependency work. It
must expose typed HTTP and dispatch outcomes, authenticated scoped versioned
events as hints, and authoritative REST state. It must include provider
migrations/backfill and comprehensive regression/integration tests.

## Acceptance Criteria

- [ ] Calibration jobs use the existing `PrintJob`, primary
  `JobQueueController`/`JobQueueService`, and
  `PrintJobManagementService` backend upload/start adapters. Creation via
  `JobQueueAnalyticsController` is unavailable or rejected.
- [ ] `PrintJob` has additive nullable fields for `JobKind` (`Standard` or
  `FilamentCalibration`), calibration project/attempt/snapshot/orchestration,
  slice/artifact provenance, creator, idempotency scope/key/request SHA-256,
  explicit firmware family/G-code dialect/slicer
  engine/distribution/version/container digest, specification/machine/process/
  filament/G-code hashes, printer configuration revision, and typed blocked
  reason code/JSON.
- [ ] Calibration provenance and compatibility fields are immutable after
  creation. Changed immutable input requires a new job and idempotency key.
  Existing rows backfill to `Standard` with nullable new fields.
- [ ] The primary `POST /api/job-queue` requires a valid stable
  `Idempotency-Key` for calibration, exact `assignedPrinterId`, `copies = 1`,
  authoritative promoted `GcodeFileId`, complete attempt/snapshot/
  orchestration/provenance and compatibility tuple/hashes, and current
  printer revision. It never auto-selects a printer or accepts raw/replacement
  artifact bytes.
- [ ] Canonical SHA-256 covers every immutable queue input, including G-code
  ID/hash, exact printer/revision, project/attempt/orchestration/provenance,
  kind/priority/copies/compatibility requirements, firmware/dialect, slicer
  tuple/digest, and all specification/profile hashes.
- [ ] A filtered unique index on `(IdempotencyScope, IdempotencyKey)` handles
  races. First winner returns `201` + `Location` + job `ETag` +
  `Idempotency-Replayed: false`; exact replay (including terminal jobs)
  returns `200` and the same job + `Idempotency-Replayed: true`; changed hash
  returns `409 idempotency_payload_mismatch`; invalid/missing key/request
  returns `400`; missing authoritative resources returns `404`; incompatible
  or stale targets return `422 calibration_job_incompatible`; authorization
  returns `401`/`403`. Concurrent losers reread and compare the winner.
- [ ] Only the winning create writes one transactional durable scheduling
  outbox event. The outbox is in the same `AppDbContext` transaction as
  relevant state changes and stores durable event ID/sequence, aggregate/job/
  printer/revision, event/schema type, reconstructable payload, timestamps,
  attempts, retry timing, and error. Publisher/consumer are idempotent and
  startup/periodic reconciliation recovers crashes. The lossy in-memory
  channel is only a wake-up optimization.
- [ ] One database-backed atomic cross-process dispatch claim service is
  called by every direct/manual/scored/batch/automatic/Desktop/generic-status/
  rerun/requeue/future scheduler start path. No path sets `Printing` or calls
  an upload/start adapter without the shared claim.
- [ ] Before claim, it verifies queued/validly assigned state, exact printer,
  enabled/available/not-maintenance, fresh authoritative online+idle
  telemetry within the capability-advertised freshness limit, no Starting/
  Printing/Paused or uncertain owner, authoritative promoted G-code/hash,
  hard material/nozzle/toolhead/model/build/required-capability compatibility,
  valid calibration records, explicit Klipper firmware and Klipper dialect,
  explicit upstream OrcaSlicer version/digest and all hashes, current printer
  configuration revision, valid exact-job acknowledgement, and hard
  filament/SKU/spool sufficiency policy. Manufacturer/model/backend never
  substitutes for explicit compatibility evidence.
- [ ] Claim transaction atomically writes `PrintJob.Status = Starting`,
  actual start time, printer active job/dispatch attempt, acknowledgement
  consumption, state history/audit, and outbox event using row versions/
  fencing. It does not hold a database transaction or global orchestration
  lock across network I/O and permits safe concurrent starts on different
  printers.
- [ ] Backend upload streams the authoritative G-code through existing
  adapters. `Printing` and success events occur only after confirmed backend
  acceptance. Known pre-start failure releases the lease, clears incorrect
  start time, preserves/re-arms safety state, and returns a typed state/result.
  Unknown outcome remains `Starting`, owns an uncertain lease, is never
  blindly retried or given another acknowledgement, and reconciles against
  backend state while preserving backend identifiers.
- [ ] `PrinterDispatchState` adds exact acknowledged job/time/actor/
  idempotency key/expiry, active job/dispatch attempt, and row version.
  Calibration no longer uses an indefinite generic pre-clear.
- [ ] `POST /api/job-queue/{jobId}/acknowledge-bed-clear-and-start` requires
  auth, a stable command idempotency key, and `If-Match`; authorizes both
  `queue:acknowledge-bed-clear` and `queue:start`; validates exact scoped
  job/printer/revision, dispatchability, fresh idle state/no lease, complete
  tuple/hashes/revision, and hard filament policy; then persists actor/time/
  key/expiry and atomically claims or writes a durable command.
- [ ] Acknowledgement endpoint returns `202` for new accepted asynchronous
  command; `200` for exact replay/already Starting/Printing; resource-hiding
  `404`; typed `409 wrong_job`, `printer_busy`, `job_not_dispatchable`, or
  idempotency mismatch; `412 dispatch_revision_conflict`; `428
  precondition_required`; `422 calibration_job_incompatible` or
  `filament_check_failed`; `503 printer_offline_or_stale`; and `401`/`403`.
- [ ] Exact-job acknowledgement is one-use and expiring. Reorder, inserted
  job, cancellation, changed firmware/configuration/profile/specification/
  G-code, expiry, or failed validation cannot let another job consume it.
  Incompatibility leaves calibration queued with a typed blocked reason and
  does not consume acknowledgement. Requeue/abort/rerun requires a new one.
- [ ] Semantic priority is Urgent > High > Normal > Low in every display,
  queue, scorer, scheduler, ready-head, reconciliation, and dispatch query.
  Undefined priority is rejected. Queue positions are changed transactionally
  or with deterministic conflict handling. `Paused` is active everywhere.
- [ ] Job and dispatch-state revisions appear in bodies and ETags.
  `If-Match` is required for acknowledgement/start, assignment, reorder,
  cancellation, and safety overrides. Expected EF conflicts map to `412`;
  semantic conflicts map to `409`.
- [ ] Typed dispatch result exposes attempt ID, state, accepted/backend
  accepted timestamps, outcome (`Accepted`, `Rejected`, `FailedBeforeStart`,
  `Unknown`), error code, retryability, reconciliation requirement, job
  revision, and dispatch-state revision.
- [ ] Durable ordered events use an authenticated SignalR hub and authorized
  farm/printer/project/job groups only, never protected `Clients.All`.
  Envelope has schema version, event ID, monotonic sequence, occurrence time,
  event type, scoped IDs, kind/status/revisions/attempt, bed-clear state, and
  typed failure. Events cover queue lifecycle, bed-clear lifecycle, claim,
  upload/outcome/reconciliation, and terminal/requeue states. No credential,
  private URL, or filesystem path leaks. Clients can detect gaps and refetch
  REST/change-feed authority.
- [ ] Permissions `queue:read`, `queue:write`, `queue:start`, `queue:cancel`,
  `queue:acknowledge-bed-clear`, and `queue:reconcile` are enforced with
  farm/printer/project/job ownership scope. Hubs/groups are authenticated.
  Reconciliation/safety overrides are operator/admin restricted. Actor,
  job/printer/attempt/operation key/acknowledgement/claim/start/cancel/
  override/reconciliation outcomes are audited without secrets.
- [ ] Provider-correct SQLite, PostgreSQL, and SQL Server core migrations add
  all fields, filtered idempotency/provenance indexes, dispatch-state changes,
  durable outbox, dispatch attempts/reconciliation, and audit data. Backfill
  is conservative: no ambiguous legacy flag becomes a valid acknowledgement
  or active lease. Migrations and model snapshots are mutually consistent.
- [ ] Standard queue requests and existing non-calibration clients remain
  backward compatible and do not acquire new calibration-only requirements.
- [ ] Tests cover first/exact/terminal/mismatched/missing-key idempotency;
  concurrent identical/conflicting inserts across separate contexts; one
  outbox winner; analytics bypass; two-instance same job/printer and
  two-job/one-printer races; Paused/uncertain/backend-active blocking; every
  start-path claim; stale/offline/maintenance/disabled/incompatible checks;
  acknowledgement replay/wrong/reorder/insert/cancel/expiry/revision and
  tuple/hash/config invalidation; filament hard gate; rerun requiring new
  acknowledgement; urgent-first/undefined priority/capabilities/explicit
  tuple; known/unknown outcomes; crash boundaries and duplicate prevention;
  outbox recovery/retry/dedup/order; authenticated group isolation/versioned
  envelope/gap recovery; authorization scope matrix/audit; secret/path
  redaction; and all provider migration/backfill behavior.
- [ ] Focused and full relevant build/test/format/compliance/migration/compose
  validation pass without new warnings. Existing repository test/lint/build
  commands are used; test output is captured once per run.
- [ ] Changes are committed with repository convention, the required Copilot
  trailers, and pushed. Exactly one non-draft PR is opened from
  `jpapiez-issue-900-calibration-dispatch` (or the app-prefixed equivalent)
  into `development`, includes `Closes #900`, is not merged, and reports CI
  and mergeability.
